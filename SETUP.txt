PulseMonitor - local telemetry analytics
======================================

Current scope: React/TypeScript dashboard, sessions/projects/keys, bounded metrics
APIs, Express SDK, Redis/BullMQ worker, PostgreSQL storage and live Socket.IO updates.
No hosted services or cloud accounts are needed. All Markdown is intentionally
ignored; this file is the public setup guide.

QUICK START: FULL APP IN DOCKER
-----------------------------
Install Node.js 22.12+ and Docker Desktop with Linux containers. From the cloned
repository, run these commands (initial dependency/image downloads need internet):

  cd backend
  npm ci
  npm run db:init
  cd ..
  docker compose -f compose.app.yaml up -d --build --wait

Open http://localhost:5173 (use localhost, not 127.0.0.1, for the browser origin).
Sign in as demo@pulsemonitor.local using SEED_PASSWORD from the root .env file.
db:init creates random credentials and never overwrites an existing .env. Keep
this file private. Initial migrations and an idempotent seed run automatically
through the initialize service before API/worker startup. Five seed events appear
on a first setup; existing seed events keep their original timestamps.

Generate finite normal/slow/500 traffic:
  docker compose -f compose.app.yaml --profile demo up -d demo
  docker compose -f compose.app.yaml exec demo node dist/demo/run-traffic.js

The default sends 30 requests: ten each to /items/:id, /slow and /fail. The worker
commits events, then live charts refetch. Choose Demo API and Last hour. You may
run the finite command again. It does not continuously generate traffic.
If the seed key was revoked, create a replacement in Projects & keys and configure
DEMO_API_KEY for the demo service; never reset your database just to recover a key.

Normal stop/start (preserves data):
  docker compose -f compose.app.yaml --profile demo stop
  docker compose -f compose.app.yaml up -d --wait

The full app uses pulsemonitor-app volumes, separate from the host-development
compose.yaml volumes. PostgreSQL and Redis are internal in the full app. Browser
port 5173 and ingestion/API port 3000 bind only to localhost. APP_PORT and API_PORT
can be set in root .env if ports conflict; FRONTEND_ORIGIN follows APP_PORT.
NODE_ENV=development is deliberate for local HTTP cookies. This is not an HTTPS
production deployment configuration. One API and one worker are supported.

Architecture:
  Express request -> SDK memory buffer -> HTTP batch -> API key + validation
    -> Redis/BullMQ -> independent worker -> PostgreSQL commit
    -> Redis Pub/Sub -> authorized Socket.IO room -> React refetches REST metrics

Dashboard:
- Login/logout, select/create projects, create/list/revoke telemetry keys.
- Counts, requests/sec, 5xx percentage, weighted mean latency, minute charts and
  endpoint pages; 15-minute, 1-hour, 6-hour and 24-hour windows.
- Loading/empty/error/session-expired states, responsive layout, keyboard focus,
  manual refresh, live connection state and REST recovery after reconnect.
- The small workspace UI shows up to 50 projects and the latest 50 keys.

Metrics contract:
  GET /api/v1/projects/:id/metrics/overview?from=<ISO>&to=<ISO>
  GET /api/v1/projects/:id/metrics/series?from=<ISO>&to=<ISO>
  GET /api/v1/projects/:id/metrics/endpoints?from=<ISO>&to=<ISO>&page=1&pageSize=20
Browser session and project ownership are required. UTC [from,to) ranges are at
most 24 hours. Rate=count/window seconds; errorRate is a 0-100 percentage of 5xx.
Latency is milliseconds, null for no data. Minute buckets include zeros and use
actual overlapping seconds for partial-minute rates. Endpoint pageSize <=50,
page <=1000; minute series <=1441 points. Queries are parameterized SQL.

Important limits:
- HTTP 202 means queued, not processed. Delivery/retries are at least once;
  project+eventId uniqueness prevents duplicate rows. Never claim exactly once.
- SDK buffering is memory-only and can lose events on exit/overflow/retry exhaustion.
- Redis AOF everysec can lose roughly the latest second on a crash; no zero-loss
  claim. Pub/Sub notifications are best-effort. Reconnect/manual refresh use REST.
- No percentile pipeline, alerts, AI, distributed scaling or performance benchmark
  claims. Raw telemetry grows until you run the explicit retention command below.

Retention (preview first; applies to all local projects):
  docker compose -f compose.app.yaml exec api node scripts/retention.cjs 7
  docker compose -f compose.app.yaml exec api node scripts/retention.cjs 7 --apply
The second command irreversibly deletes events older than seven days. It keeps
projects, accounts and keys. Change 7 to a whole number from 1 to 365.
Destructive reset: docker compose -f compose.app.yaml --profile demo down -v
Only use that if you intentionally want to delete this full app's database and
queue volumes. Ordinary stop/down without -v preserves volumes.

Verification commands:

E2E expects the full Docker app at localhost:5173 and backend compiled first.
It creates a demo project/key, sends SDK traffic, checks live charts/reconnect,
revokes its key, and saves desktop/mobile screenshots under artifacts/. It leaves
its project/events for inspection. APP_URL overrides its browser target.
GitHub Actions runs these checks and container/browser verification. Local results
do not prove a hosted Actions run; check the Actions tab after pushing.

Troubleshooting:
- Docker pipe/engine errors: open Docker Desktop and wait for Engine running.
- Port conflict: stop another local API/Vite process or change APP_PORT/API_PORT.
- Empty charts: select the right project/time window, generate traffic, inspect
  docker compose -f compose.app.yaml logs --tail 30 worker api, then Refresh.
- Offline indicator: use the configured localhost origin, allow WebSockets and
  check the API/Redis containers. Manual Refresh still works without live updates.
- Expired session: sign in again; a new login invalidates the previous session.
- Keys are shown only once. Create another if lost; revoke keys no longer needed.
- Credentials changed after initialization? Seed intentionally does not overwrite
  an existing password/key. Use the original root .env for that database volume.

Database details
----------------
Compose service: postgres
Image: postgres:17.11-alpine3.23 (startup and database checks verified)
Host endpoint: 127.0.0.1:5433 by default
Container port: 5432
User/database: pulsemonitor
Volume: Compose-managed postgres_data
Health probe: pg_isready
Local demo owner: demo@pulsemonitor.local
Demo password/API key: SEED_PASSWORD and SEED_API_KEY in root .env, not printed.

Use a database viewer with these local settings if desired. Do not share the
connection password. No viewer or hosted account is required.

Seed records use reserved stable IDs. Rerunning seed does not rotate passwords,
reactivate revoked keys, overwrite project edits, refresh old event timestamps or
delete unrelated data. Changing SEED_PASSWORD/SEED_API_KEY after the first seed
does not change existing database credentials.

Authentication exercise (verified in Windows PowerShell, from backend/)
---------------------------------------------------------------------
Keep npm start running in one terminal. In a second PowerShell terminal:

  $demoPassword = (Get-Content ../.env | Where-Object { $_ -like 'SEED_PASSWORD=*' }).Split('=', 2)[1]
  $loginBody = @{ email = 'demo@pulsemonitor.local'; password = $demoPassword } | ConvertTo-Json
  $authHeaders = @{ 'X-PulseMonitor-Request' = '1' }
  Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/auth/login -ContentType application/json -Headers $authHeaders -Body $loginBody -SessionVariable demoSession
  Invoke-RestMethod -Uri http://localhost:3000/api/v1/auth/me -WebSession $demoSession
  Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/auth/logout -Headers $authHeaders -WebSession $demoSession
  Invoke-RestMethod -Uri http://localhost:3000/api/v1/auth/me -WebSession $demoSession
  Remove-Variable demoPassword,loginBody,demoSession

Expected: login and me return only user id/name/email; logout returns 204 with no
body; the final me request reports 401 Unauthorized. Do not print the password,
request body or cookie. Adjust port 3000 if you changed PORT. Ctrl+C stops the API.

Sessions last eight hours. A new login replaces the previous login for that user.
PostgreSQL stores only the token hash. Logout deletes that session server-side.
Login allows ten attempts per IP per 15 minutes; 429 includes Retry-After. Limits
are in memory, capped at 1,000 IP entries and reset when the API process restarts.

Browser integration for the future frontend:
- FRONTEND_ORIGIN defaults to http://localhost:5173. Set an exact origin with no
  trailing slash in backend/.env. Use localhost for both frontend and API.
- Send JSON on login; use credentials: 'include' on authenticated fetch calls.
- POST requests require X-PulseMonitor-Request: 1. This and exact-origin CORS
  protect cookie writes; SameSite=Strict adds another browser restriction.
- Session cookies use HttpOnly. NODE_ENV=production also sets Secure, requiring
  HTTPS. Use development mode for the local HTTP demo.
- Real browser integration will be tested when the frontend exists in phase 8.

The new migration changes event uniqueness from eventId globally to
(projectId, eventId). A retry in one project conflicts; another project may use
the same event ID. This alone does not implement the future telemetry worker.

Projects and API keys exercise (Windows PowerShell, from backend/)
----------------------------------------------------------------
Keep npm start running. This creates a local project and a key, then revokes only
that new key. Existing demo project and seed key are left intact. Each run adds
another exercise project; there is no project-delete endpoint in this small scope.

  $demoPassword = (Get-Content ../.env | Where-Object { $_ -like 'SEED_PASSWORD=*' }).Split('=', 2)[1]
  $loginBody = @{ email = 'demo@pulsemonitor.local'; password = $demoPassword } | ConvertTo-Json
  $authHeaders = @{ 'X-PulseMonitor-Request' = '1' }
  Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/auth/login -ContentType application/json -Headers $authHeaders -Body $loginBody -SessionVariable demoSession | Out-Null
  $projectBody = @{ name = 'Phase 4 exercise'; environment = 'development' } | ConvertTo-Json
  $createdProject = Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/projects -ContentType application/json -Headers $authHeaders -Body $projectBody -WebSession $demoSession
  $projectId = $createdProject.project.id
  Invoke-RestMethod -Uri "http://localhost:3000/api/v1/projects/$projectId" -WebSession $demoSession
  Invoke-RestMethod -Uri 'http://localhost:3000/api/v1/projects?page=1&pageSize=20' -WebSession $demoSession
  $keyBody = @{ name = 'Exercise key' } | ConvertTo-Json
  $createdKey = Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/v1/projects/$projectId/keys" -ContentType application/json -Headers $authHeaders -Body $keyBody -WebSession $demoSession
  $createdKey.apiKey
  Invoke-RestMethod -Uri "http://localhost:3000/api/v1/projects/$projectId/keys" -WebSession $demoSession
  $keyId = $createdKey.apiKey.id
  Invoke-RestMethod -Method Post -Uri "http://localhost:3000/api/v1/projects/$projectId/keys/$keyId/revoke" -Headers $authHeaders -WebSession $demoSession
  Invoke-RestMethod -Uri "http://localhost:3000/api/v1/projects/$projectId/keys" -WebSession $demoSession
  Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/auth/logout -Headers $authHeaders -WebSession $demoSession
  Remove-Variable demoPassword,loginBody,demoSession,createdKey

Expected: project/key creation returns 201; reads return 200; revoke returns 204.
The creation response includes rawKey (kept in $createdKey in the exercise) and
safe apiKey metadata. The raw key cannot be retrieved again. Lists show only
id/name/keyPrefix/createdAt/revokedAt, never the hash or raw credential. After
revocation, revokedAt contains a timestamp. Repeated revocation returns 204.

Project and key lists accept page=1..1000 and pageSize=1..50 (default 20) and
return page/pageSize/hasMore. Records are sorted newest first with ID tie-breaking.
Project names and key names: 1-80 trimmed characters; descriptions: up to 500.
Environment: development (default), test, staging or production. Unknown fields
are rejected. Missing and unowned project IDs both return 404.

User sessions manage projects/keys. The ingestion endpoint authenticates from
X-API-Key, deriving the project from the database.
Do not put raw keys in Git, public frontend
bundles or URL queries. Revocation rejects subsequent authentication but cannot
cancel already authenticated requests or previously accepted jobs.

Run the finite telemetry demo
-----------------------------
After setup/migrations/seed above, stop any manually started API, worker or demo
processes, then run from backend/:
  npm run demo

This starts one API, one independent worker and a demo Express app on temporary
local ports. It generates 30 requests (10 normal, 10 slow, 10 intentional 500s),
flushes the SDK, verifies the matching 30 PostgreSQL events, then stops its Node
child processes. PostgreSQL/Redis stay running. Successful output includes
demo_verified with requests:30 and stored:30. This flow was verified locally.
These are correctness counts, not a throughput benchmark. Each run adds fresh
events with a unique demo service label for later charts.

The seeded key is used by default. If revoked, create a key through phase 4 and
put DEMO_API_KEY in the ignored root .env. Do not change SEED_API_KEY expecting
the seed to rotate existing credentials. Optional DEMO_REQUESTS is 1-300; default 30.

Separate-process learning exercise, from backend/ in separate terminals:
  npm run build
  npm start
  npm run worker
  npm run demo:api
  npm run demo:traffic

The last command sends a finite run and exits; it is not continuous load.
API default: localhost:3000. Demo default: 127.0.0.1:4000.
Do not run npm run demo alongside these processes: queue admission supports one
API producer process. Stop Node processes with Ctrl+C when finished.

To observe asynchronous processing: stop only the worker, run demo:traffic,
then restart the worker. Accepted jobs wait in Redis and are persisted afterward.
To observe SDK failure isolation: stop the collector API, keep demo:api running,
and run demo:traffic. Business responses remain 200/500 as designed; telemetry
can be dropped after bounded retries. Restart the collector and generate fresh traffic.

Collector protocol and limits
-----------------------------
POST /api/v1/telemetry/batch with Content-Type: application/json, X-API-Key and
body {"events":[...]}. There is no user-session/cookie requirement on this sender
endpoint. Allowed event fields:
  eventId: UUID; requestId: 1-80 letters/digits/_/-;
  service: 1-64 letters/digits/_/-;
  environment: development/test/staging/production;
  route: normalized template such as /items/:id (maximum 160 characters, no query);
  method: GET/POST/PUT/PATCH/DELETE/OPTIONS/HEAD;
  statusCode: integer 100-599; responseTime: 0-60000 milliseconds;
  timestamp: ISO date/time within the previous 24 hours or next five minutes.

Only events may appear at the top level; projectId is derived from the API key.
Maximum 50 events per batch and 100kb JSON body. 202/status:queued means Redis
acknowledged admission, not that PostgreSQL processing finished. 429 rate limits
and 503 queue errors include Retry-After. Retries must reuse event IDs.

The single API admission gate bounds unfinished work to 100 batch jobs, including
active/delayed/paused jobs. Concurrent admission gets a retryable 503 rather than
an in-memory waiting list. At most 60 attempts/project/minute. Do not bypass this
gate with another API producer or manual job retries. On an uncertain enqueue
acknowledgement, admission stops until the API is restarted; the job may already
exist. Replay is safe because PostgreSQL uniquely identifies (projectId,eventId).

Worker concurrency: 2; processing attempts: 3 with exponential backoff starting
at 1 second. Permanent validation/constraint failures do not retry. Keep at most
100 completed and 100 failed jobs; event stream is approximately trimmed to 1000.
Failed jobs are not replayed automatically after exhausting their attempts.

Redis: redis:7.4.11-alpine3.21, host 127.0.0.1:6380 by default (REDIS_PORT in root
.env), named redis_data volume, AOF everysec, 128mb/noeviction. Local tooling builds
a loopback REDIS_URL rather than using an unrelated URL from your environment.
A clean Redis stop/start preserved a waiting job in verification. A crash can
still lose recent acknowledged writes; no exactly-once or zero-loss claim is made.

SDK defaults: 500 events including in-flight batches; newest-overflow drop;
20 events/batch; partial flush every second; one sender; one-second HTTP timeout;
three attempts; 250ms exponential backoff; Retry-After capped at five seconds;
three-second best-effort shutdown flush. The demo uses a five-second send timeout
and seven-second shutdown flush to tolerate local cold starts. Unsent memory
buffers can be lost on crash, overflow, retries exhausted or shutdown deadline.
stats().queued means accepted, not processed. No request bodies, credentials or
raw sensitive query strings are captured. No disk spool/replay is implemented.

Infrastructure commands:
  npm run services:start  # start PostgreSQL and Redis, wait for health
  npm run services:stop   # stop both, preserve named volumes
  npm run redis:stop
  npm run redis:start
  npm run test:redis      # explicitly interrupts Redis to check clean-restart persistence

it does not delete the real telemetry queue or database records.

Troubleshooting and data safety
------------------------------
- Docker not found: install/start Docker Desktop and reopen the terminal/editor.
- Docker engine unavailable: wait for startup; use Linux containers/WSL 2.
- Port conflict: change POSTGRES_PORT in root .env before starting this container.
- Changing POSTGRES_PASSWORD in .env does not change an already initialized
  database password. Keep the original value unless deliberately rotating it.
- Use npm run db:status to check the service and npm run db:migrations for history.
- Do not use prisma migrate reset or docker compose down -v as normal setup.
  Reset/drop-volume commands delete data. No automatic reset command is provided.

Windows: Docker installed but engine not running
------------------------------------------------
Check: wsl --version
If WSL is missing, open PowerShell as administrator and run:
  wsl --install --no-distribution
Restart Windows when prompted. Then run:
  wsl --update
  wsl --version
Open Docker Desktop, complete its first-run prompts and use the WSL 2 engine.
Reopen your terminal and run docker version; both Client and Server must appear.
A separate Ubuntu distribution is not required for commands from PowerShell.
Official guidance:
https://learn.microsoft.com/en-us/windows/wsl/basic-commands
https://docs.docker.com/desktop/features/wsl/
